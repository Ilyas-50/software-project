Code-Based (Bolt.new) vs Low-Code: Comparative Assessment
How to read this document

Every statement about the low-code version is an assumption to verify. The low-code app does not exist yet, so nothing about it is confirmed. Each low-code row below tells you what evidence you would need to collect to convert the assumption into a verified fact. The code-based column is grounded in the files I just read.

1. Correctness against the same requirements
Code-based (observed)

The deterministic rules live in src/lib/availability.ts as a pure function checkAvailability({ start, duration, blocked, bookings, now }) returning { available, reasonCode, message }. The six criteria map to reason codes:

AC	Rule	Code evidence	Reason code
AC1	Start in the future	if (start <= now) line 59	PAST_START
AC2	Duration > 0 and <= 120	Lines 68 and 76	DURATION_ZERO / DURATION_TOO_LONG
AC3	Overlap unavailable	Lines 94-103, start < booking.end && booking.start < end	OVERLAP
AC4	Blocked room unavailable	Line 85	ROOM_BLOCKED
AC5	Decision without mutation	Function reads bookings via for...of, never writes; T8 confirms	OK
AC6	Invalid input feedback	Lines 43-56 reject non-integer/out-of-range/non-finite	INVALID_INPUT

Test evidence (real, from run_availability_tests.mjs): 15/15 assertions pass across T1-T8. Touching endpoints (T7) correctly return OK because the overlap predicate is strict on both sides.

One observable gap in the code-based version: the test file (run_availability_tests.mjs) hand-copies the rule logic instead of importing availability.ts. If the two drift, tests pass while production breaks. Evidence needed to confirm drift hasn't happened: a diff of the checkAvailability function body in both files, or adding a real TS test runner.

Low-code (assumption to verify)

Low-code platforms (Appsmith, Budibase, Power Apps) would express these rules in a formula/JS snippet inside a widget's onClick or a query transformer. To assess correctness you would need:

Evidence to collect: a screenshot or export of the formula/JS block that implements each AC, plus a run of the same T1-T8 inputs through the live app. The overlap predicate (start < exEnd && exStart < end) is easy to get wrong in a formula (<= instead of < would break T7).
Assumed risk: low-code formula engines may coerce types (string "60" vs number 60), which could make the duration boundary checks behave differently. Verify by testing T4 and T5 with string inputs.

Summary

The code-based version has verified test evidence (15/15 T1-T8 assertions pass) and a clean separation of deterministic rules from presentation. Its main weakness is test-logic duplication: the tests copy the rule function rather than importing it, so they prove the copy works, not the shipped module.

Every claim about the low-code version is an assumption. Low-code may be faster to build for simple CRUD, but the six-rule validation contract with structured reason codes is exactly the kind of logic that is hard to express in a formula and hard to unit-test in a widget. Security is not guaranteed by the platform — you must verify HTML escaping, public-sharing exposure, and credential isolation per platform with the concrete tests above.
